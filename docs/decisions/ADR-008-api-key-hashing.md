# ADR-008: API keys are random, hashed with SHA-256 (not bcrypt), shown once

## Status

Accepted

## Date

2026-10-18

## Context

Team members connect external MCP clients (Claude Code, Cursor, Inspector) to the gateway with a personal API key. The assignment requires per-user, revocable, hashed keys. The gateway checks the key on every `/mcp` request, so verification must be cheap, and revocation must take effect immediately. Passwords (chosen by humans) and API keys (generated by us) have very different entropy.

## Decision

- A key is `ugw_` + 32 random bytes encoded in base62.
- Only `SHA-256(key)` is stored (`api_keys.key_hash`, unique), plus a display prefix (the first 12 characters) so users can recognise a key in the list.
- The plaintext is returned **once** at creation, in a "shown once" dialog with ready-to-paste client config. It cannot be recovered afterwards; the remedy is to revoke and generate a new key.
- Revocation sets `revoked_at`. There is **no auth cache**, so the very next request after revocation is rejected. Disabling a user also revokes their sessions and keys.
- User **passwords** are different: they are hashed with argon2id (minimum 10 characters), because humans choose low-entropy secrets.

## Alternatives considered

- **bcrypt or argon2 for API keys.** Rejected: slow hashes exist to make guessing low-entropy secrets expensive. A 32-byte random key cannot be brute-forced regardless of hash speed, so a slow hash adds per-request CPU cost with no security gain. This is the same reasoning GitHub uses for its tokens.
- **Storing keys in plaintext or reversibly encrypted.** Rejected: a database leak or backup would expose usable keys, and "shown once" would not be true.
- **Self-contained signed tokens (for example JWTs) as long-lived API keys.** Rejected: revocation requires a database lookup anyway, and it would not give us a displayable prefix and revoke-by-row model. (We do use a short-lived signed token for the internal chat path; see ADR-010.)

## Consequences/trade-offs

- A database read exposes hashes, not usable keys; lookup is a single indexed query by hash.
- A lost key cannot be shown again; users must rotate it.
- Revocation is immediate, at the cost of a database lookup per `/mcp` request (we accept this; no caching of auth decisions).
- Security rests on key generation using a cryptographically secure random source and on never logging keys (pino redaction covers `authorization`).
- Implementation and unit tests (generation, hashing) arrive in a later phase.

## Revisit if

- Keys ever become user-chosen or short, which would need a slow hash or rate limiting.
- Per-request DB lookup becomes a bottleneck (a cache would weaken immediate revocation, so that trade-off would need its own ADR).
