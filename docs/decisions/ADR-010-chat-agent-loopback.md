# ADR-010: Chat agent loops back through the real `/mcp` with a 5-minute internal token

## Status

Accepted. **Token and `/mcp` acceptance implemented in Phase 3** (2026-10-19); **the chat agent, the loopback client and `POST /api/chat` implemented in Phase 4** (2026-10-19). One change from the Decision below: a fresh token is minted for **every HTTP request** the loopback client makes, not once per turn (see "As built (Phase 4)").

## Date

2026-10-18

## Context

The dashboard has a chat agent: an LLM tool loop that answers questions by calling the same tools external clients see. The assignment requires that it call tools through the gateway and act as the logged-in user. Everything the agent does must go through the same authentication, routing, timeout, size-limit and audit path as an external MCP client, so the chat cannot become a back door with different rules.

## Decision

- `POST /api/chat` (session cookie) mints a short-lived **internal token**: a JWT signed (HMAC) with `GATEWAY_INTERNAL_TOKEN_SECRET`, `sub` = user id, `aud` = `gateway-chat`, expiry 5 minutes.
- The agent then calls the gateway's own `/mcp` endpoint over HTTP loopback with `Authorization: Bearer <internal token>`, for both `tools/list` and `tools/call`. `/mcp` accepts this token alongside API keys.
- Calls made this way are audited with `source=chat` and attributed to the real user.
- The token never leaves the server and is never sent to the browser or the LLM.
- Agent limits: at most 8 tool steps per turn, tool results truncated to 6,000 characters, and a 60s total turn timeout. Tool output is wrapped as untrusted data in the prompt.

## Alternatives considered

- **Call the internal tool-routing functions directly (no HTTP).** Rejected: it would create a second code path that could drift from `/mcp` in auth, tool visibility, limits and auditing, and the chat would stop being a faithful test of the real endpoint.
- **Give the chat agent a real stored API key per user.** Rejected: it creates long-lived hashed rows to clean up and shows up in users' key lists, when a 5-minute stateless token is enough.
- **A single service account with broad rights.** Rejected: it would lose per-user attribution and "acts as the user".

## Consequences/trade-offs

- One enforcement and audit path: anything true for external clients is true for chat, and the chat exercises `/mcp` end to end.
- Costs an extra in-process HTTP hop and the gateway must accept two kinds of bearer credentials, so the token validation (audience, expiry, signature) needs careful tests.
- `GATEWAY_INTERNAL_TOKEN_SECRET` becomes another sensitive secret in `gateway-secrets`.
- Internal tokens cannot be revoked individually; they simply expire after 5 minutes. The spec does not say whether a token for a user disabled mid-turn is rejected, so that must be decided and tested at implementation time.
- The token and its acceptance by `/mcp` were built in Phase 3; the agent loop, the loopback client and `POST /api/chat` in Phase 4.

## As built (Phase 3)

- `apps/gateway/src/auth/internalToken.ts`: `mintInternalToken(userId, secret, ttlSec = 300)` signs an HS256 JWT with `sub` = user id, `aud` = `gateway-chat`, `iss` = `urumi-gateway`, `iat`, `exp = iat + 300`.
- `verifyInternalToken` uses `algorithms: ['HS256']` (so `alg: none` and any other algorithm are rejected), checks audience and issuer, requires `sub`, `iat` and `exp`, requires `sub` to be a UUID, and allows a **5 s clock tolerance**. The signature is checked before any claim, so a forged token is `invalid`, never `expired`. A rejected token reveals no reason or claim.
- **The open question in this ADR is decided:** `/mcp` **re-reads the user on every use**; a token for a user who was disabled after it was minted is rejected (audit `auth_rejected`, message `user disabled`), and an expired one too (`internal token expired`). Tested in `test/auth/bearer.test.ts` and `internalToken.test.ts`.
- An accepted token yields `source = 'chat'` on the call context, so audit rows say `chat` and carry the real user, with `api_key_id` null.
- Tokens still cannot be revoked individually (5-minute expiry). In Phase 3 nothing minted or presented one yet; Phase 4's loopback client does (below).
- `GATEWAY_INTERNAL_TOKEN_SECRET` (at least 32 characters) is generated by Helm in Secret `gateway-secrets`.

## As built (Phase 4)

- **A token per request, not per turn.** `connectLoopback(mcpUrl, mintToken)` (`apps/gateway/src/chat/mcpLoopback.ts`) builds a real `@modelcontextprotocol/client` 2.3.1 client with a `StreamableHTTPClientTransport` whose custom `fetch` calls `mintToken()` and sets `Authorization: Bearer <token>` on **every** HTTP request (connect, `tools/list`, each `tools/call`). Why the change (asked for by the Phase 3 final review): a token minted once per turn couples the token lifetime to the turn timeout. `CHAT_TURN_TIMEOUT_MS` is at most 120 s today, but minting per request costs only one HMAC and means no turn can ever outlive its 300 s token, whatever the timeouts become. The token is minted with the gateway's clock (`deps.clock()`), the same clock `/mcp` verifies with. A test that counts mints per HTTP request does not exist (a deferred minor).
- `mcpUrl` is `http://127.0.0.1:<port>/mcp`, known once the server listens (`MCP_ALLOWED_HOSTS` already contains `127.0.0.1`).
- **The agent loop** (`chat/agent.ts`): `tools/list` once per turn, descriptions cut to 300 characters; tool calls run one at a time; each result goes back as `<tool_result name="…">` cut to 6,000 characters, and a result cannot close its own block (`<tool_result` inside it is rewritten to `<tool-result`); arguments that are not a JSON object become a tool error and the tool is not called. The turn ends with `final`, `max_steps` (after 8 steps) or `timeout` (60 s, or the browser closed the connection).
- **The trace returned to the browser** is `toolCalls[{name, arguments, outcome, durationMs, resultPreview}]`: `arguments` is the parsed object (the spec's earlier name was `args`; the spec now says `arguments`), or the raw text cut to 500 characters when it did not parse; `resultPreview` is at most 500 characters.
- **Limits per user** (`chat/service.ts`): one turn in flight (`409 CONFLICT` "A reply is already being generated", checked before the rate limiter so a refused duplicate costs no turn) and `CHAT_RATE_LIMIT_PER_MIN` (10) turns a minute (`429 RATE_LIMITED` with `Retry-After`).
- **What the loopback client hides:** a tool call rejected with HTTP 401/403 becomes a tool error "The gateway rejected this tool call (HTTP 401): this account cannot use tools right now."; any other failure "The tool call failed before a result was returned." SDK and transport messages are never passed to the model (they can quote URLs and bodies).
- **Verified live (2026-10-19):** chat turns through the dashboard called `woo__create_product`, `woo__list_orders`, `notes__create_note`, `notes__list_notes` and `utils__calculate`; every call is an audit row with source **Chat**, the admin as user and no API key. **Tested:** a user disabled during a turn gets `HTTP 401` on the next tool call and an `auth_rejected` row `user disabled`; a client that disconnects stops its turn and frees its slot.
- **Known limits (deferred minors):** the loopback connect has its own 10 s timeout and ignores the turn signal; a failure of the loopback connect or `tools/list` answers a generic `500 INTERNAL`; a client disconnect is logged as `stoppedReason: timeout`.

## Revisit if

- The gateway is split into separate processes where loopback no longer applies.
- We need per-conversation scoping of tools.
